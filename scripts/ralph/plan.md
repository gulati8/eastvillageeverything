# Launch plan: East Village Everything iOS

Tasks to get the iOS app into the App Store with the content right. This file is
the work queue. The checkboxes are the only record of progress. Facts a later
iteration needs go in `scripts/ralph/progress.txt`, not here.

Each task has a `Done when` line, which is the verification the agent must run
before ticking it. Tasks tagged `[HUMAN]` are done by a person, who ticks them.
`Blocked by` lists tasks that must be ticked first.

## Phase 1: production uploads (S3) and image sizes

Today `STORAGE_BACKEND` is `local` on prod with no volume, and the admin runs in a different container from the app that serves `/uploads`, so an uploaded photo is unreachable and lost on the next deploy. The spec is `docs/aws-setup.md`.

- [x] **1.1 Create the S3 bucket and IAM user with the AWS CLI**, following `docs/aws-setup.md` sections 1 to 4 exactly: bucket `eastvillageeverything-uploads` in `us-east-1`, bucket policy granting public read on `public/*` only, IAM user `eve-uploads` with the inline least-privilege policy from section 2, one access key pair. Save the key pair to the root `.env` as `STORAGE_AWS_ACCESS_KEY_ID` and `STORAGE_AWS_SECRET_ACCESS_KEY`. Never print the secret.
  Done when: `aws s3api head-bucket --bucket eastvillageeverything-uploads` succeeds, `aws iam list-access-keys --user-name eve-uploads` shows one key, and a test object put with those keys to `public/test.txt` is readable by `curl` without auth, then deleted. No commit.
- [x] **1.2 Write a host-only storage env file on the EC2 box.** The deploy workflow rewrites `/srv/eve/.env` on every run, so storage secrets go in a separate `/srv/eve/.env.storage` written once over SSH (mode 600): `STORAGE_BACKEND=s3`, `STORAGE_S3_BUCKET=eastvillageeverything-uploads`, `STORAGE_S3_REGION=us-east-1`, `STORAGE_S3_PREFIX=public`, `STORAGE_S3_URL_PATTERN=https://eastvillageeverything-uploads.s3.us-east-1.amazonaws.com/{key}`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`. The last two take their values from the local `.env` entries `STORAGE_AWS_ACCESS_KEY_ID` and `STORAGE_AWS_SECRET_ACCESS_KEY`; the names differ on purpose, because `@eve/storage` reads no AWS variable itself and relies on the AWS SDK's default credential chain, which looks for the `AWS_` names. Pipe the values over the SSH session; do not echo them.
  Done when: `ssh ec2-user@100.29.233.41 'sudo cut -d= -f1 /srv/eve/.env.storage; sudo stat -c %a /srv/eve/.env.storage'` lists the seven keys and prints 600. No commit.
- [x] **1.3 Make both containers read the storage env file.** In `deploy/docker-compose.prod.yml`, add `env_file: [.env, .env.storage]` to the `app` and `admin` services (admin is where uploads happen). Neither service uses `env_file` today; injecting the whole `.env` into both is intended. Remove the now-redundant `STORAGE_*` `environment:` lines from `admin` (they are on `admin`, not `app`). Also add a line to the SSM deploy step in `deploy.yml` that creates an empty `/srv/eve/.env.storage` if it does not exist, because compose fails on a missing `env_file`. Push to deploy.
  Done when: the deploy workflow passes and `ssh ec2-user@100.29.233.41 'sudo docker exec eve-admin env | grep -c "^STORAGE_\|^AWS_"'` prints 7, same for `eve-app`. Prefix: `feat(deploy)`.
