# Plan: blank fields, Android, photo gallery, neighborhoods

Four pieces of work the user asked for on 2026-11-05, after the editorial plan
finished and the iOS app went live in the App Store: a small admin bug, the
Android version of the app on Google Play, swiping through a place's photos on
the detail screen, and letting the app cover neighborhoods beyond the East
Village. This file is the work queue. The checkboxes are the only record of
progress. Facts a later iteration needs go in `scripts/ralph/progress.txt`,
not here. The previous plan (slugs, sections, editorial) is archived in
`scripts/ralph/archive/admin-editorial-plan.md`.

Each task has a `Done when` line, which is the verification the agent must run
before ticking it. Tasks tagged `[HUMAN]` are done by a person, who ticks them.
`Blocked by` lists tasks that must be ticked first.

Decisions already made with the user, which the tasks below implement and no
task may revisit:

- **A blank text field clears the column.** `PlaceModel.update` already turns
  `''` into `NULL` (`data.x || null`); the only bug is that `readForm` in the
  admin turns a blank into `undefined`, which the model reads as "unchanged".
  Blank fields are stored as `NULL`, never `''`, because `PlaceRow.tsx` in the
  app renders a specials line whenever `specials != null`. The legacy EJS
  admin has the same bug for the editorial fields and is not fixed; it is
  being retired.
- **Android builds run on EAS's servers; the emulator runs here.** This Mac
  has no JDK or Android SDK. Builds use `eas build --platform android` without
  `--local` (the project is already linked: owner `gulati_labs`, project
  `77bcb731-ca9f-4298-85fb-d147d25de2e8`, and cloud builds ran in May). The
  JDK and SDK are installed only so the emulator can run the APK for smoke
  tests and for the human device pass, since the user has no Android phone.
  The upload keystore is generated by EAS if it will do so non-interactively,
  otherwise locally with `keytool` and sent with the build through
  `credentials.json` (gitignored). Either way Play App Signing holds the app
  signing key, so a lost upload key is recoverable.
- **The Play developer account is `gulatilabs.me@gmail.com`.** Whether it is a
  personal or an organization account is unknown; 2.4 records it. Google
  requires a personal account registered after November 2023 to run a closed
  test with at least 12 opted-in testers for 14 days before it may apply for
  production access; an organization account is exempt. The plan ships to the
  internal testing track first either way and the human decides the track
  after that.
- **The first Android release is the app as it stands (1.0.0).** It ships
  before the photo gallery and neighborhoods so the store setup is not waiting
  on new features. Version numbers: `expo.version` is bumped for every release
  that changes the JS (it is the TanStack cache buster and the
  `runtimeVersion`), `ios.buildNumber` and `android.versionCode` are bumped
  for every store build of their platform. Today: 1.0.0, iOS build 12. The
  Android release of 1.0.0 is `versionCode` 1. The photo release is 1.1.0
  (iOS 13, Android 2); the neighborhoods release is 1.2.0 (iOS 14, Android 3).
- **Photo gallery, app-only.** `GET /api/places/:id` already returns
  `photos: PlacePhotoResponse[]` (uploads first in `position` order, each with
  `credit`; or a single Google entry with `id: null` and `attribution`; or
  `[]`). The detail hero becomes a horizontally paged gallery of
  `hero_url ?? url` for every entry, 300 tall as today, with the place name
  still overlaid on it, page dots when there is more than one photo, and the
  existing "Photo: <name>" caption line under the hero showing the current
  photo's `credit` or `attribution`. When `photos` is missing (the detail query
  is seeded from the list row and refetches at once) or empty, the gallery
  shows the single `photoHero` as today, so nothing flickers. No new native
  dependency: a `FlatList` with `pagingEnabled`. List rows do not change.
- **Neighborhoods are a mobile feature. The website is not touched** (it will
  be retired or rebuilt). The public API gains a `neighborhood` filter and
  each place response carries its neighborhood's `value` and `display`. The
  app keeps fetching the whole unfiltered list (352 rows; switching is then
  instant and works offline) and filters client-side by the selected
  neighborhood, which is remembered on the device. Saved places ignore the
  neighborhood filter: a saved list is the user's own. The admin's
  "East Village" assumptions (hard-coded default slug, enrichment query,
  editorial prompt) go away. Out-of-area places already in the data (Lower
  East Side, West Village, Nolita, SoHo and whatever else the addresses show)
  get real neighborhood rows and are reassigned by the agent from the evidence
  (address, zip, coordinates), with the list logged so the human can correct
  any through the admin. The brand stays "East Village Everything" everywhere.
- **The neighborhood switcher UI is decided from mockups, not built first.**
  4.1 draws three options as a static HTML mockup in `docs/mockups/`; 4.2 is
  the human choosing one; the mobile build task is blocked until then. Option
  A is the user's own idea: the eyebrow line always reads "East Village
  Everything", and the big italic masthead title becomes the neighborhood
  name with a chevron, tappable to pick another. Options B and C are the
  agent's alternatives.
