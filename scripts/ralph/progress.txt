## Codebase Patterns
- Static public pages (privacy, support) are plain Express routes in `src/routes/public.ts` rendering full-page EJS views in `src/views/public/` (no shared layout partial; `index.ejs` and `privacy.ejs` each carry the header). Page-specific prose styles live under `.row.main-content.page` at the bottom of `public/css/main.css`; the Dockerfile copies `public/` and `src/views/` so no build step is involved. Playwright e2e (`tests/e2e/`) is NOT in CI and its browsers are not installed on this laptop: `npx playwright install chromium` under Node 26 downloads fully, then stalls during extraction (twice, 10+ minutes each), so verify public pages by starting the server (`DATABASE_URL=postgres://eve:eve_dev_password@127.0.0.1:5435/eve_development REDIS_URL=redis://127.0.0.1:6381 SESSION_SECRET=x npx tsx src/server.ts`) and using curl. Support email for the app is `amit@gulatilabs.me` (5.1), hardcoded as `SUPPORT_EMAIL` in `src/routes/public.ts`.
- Google `hours_json.weekdayDescriptions` is Monday-first (index 0 = Monday, 6 = Sunday) while `period.open.day` and JS `getDay()` are Sunday-first; `todayHoursLabel()` in `apps/mobile/src/data/transformPlace.ts` does the `(etDay + 6) % 7` rotation in Eastern Time via `getETWeekday()` from `signals/hours.ts`. Any mobile test whose module transitively imports `signals/hours.ts` must start with `jest.mock('@eve/shared-types', () => ({ EVE_TIMEZONE: 'America/New_York' }))` because the shared-types `src/index.ts` re-exports with `.js` extensions that CommonJS Jest cannot resolve for a runtime value (type-only imports are erased and never hit this). Prod `hours_json` also carries `openNow` and `nextCloseTime` keys that are not in the `HoursJson` type; they are frozen at enrichment time, so never read them.
- `places.google_place_id` has a UNIQUE constraint (`places_google_place_id_key`). When Text Search resolves two rows to the same Google place (a duplicate listing such as "The Phoenix"/"Phoenix", or a wrong match on a neighbor), the second write fails with Postgres 23505 and the script marks that row `failed`; the log line is `DB write failed ... duplicate key`, not a Google error. 35 of the 38 failures in 2.7 were this. The backfill query is `google_place_id IS NULL`, so `failed` rows are retried automatically on the next `npm run enrich`; fix for 3.3 is delete the duplicate or correct the address, then re-run, with no status reset. Rows with a NULL `address` (Club Groove) are never selected by the backfill and stay `'pending'`.
- Prod DB access for scripts: `eve-db` publishes no port, and the `eve-app` image has no `scripts/` dir or `tsx`, so run scripts from the laptop through an SSH tunnel to the container IP on the compose `internal` network: `IP=$(ssh ec2-user@100.29.233.41 "sudo docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' eve-db")` (172.21.0.3 as of 2.6; re-read it, it can change on recreate), then `ssh -f -N -M -S /tmp/eve-db-tunnel.sock -o ExitOnForwardFailure=yes -L 127.0.0.1:15432:$IP:5432 ec2-user@100.29.233.41`, build `DATABASE_URL=postgres://eve:<url-encoded POSTGRES_PASSWORD from /srv/eve/.env>@127.0.0.1:15432/eve_production` in a shell variable without echoing it, run, then `ssh -S /tmp/eve-db-tunnel.sock -O exit ec2-user@100.29.233.41`. Prod `enrichment_status` values for never-enriched rows are the 9-char literal `'pending'` WITH single quotes (an import artifact); the script writes `ok`/`failed` without quotes, so group-by queries show both styles and `enrichment_status = 'pending'` matches nothing.
- Enrichment script (`scripts/enrich-places.ts`): Text Search returns a BARE place id (`ChIJ...`); the details endpoint needs `places/<id>`, which the script now prepends. `google_place_id` stores the bare id. The script writes `enrichment_status = 'ok'` on success (not `enriched`, which the 2.7 Done when names); `lat`/`lng` are written with COALESCE so a missing `location` never nulls existing coordinates. `--limit N` and `--dry-run` are supported (`--dry-run` still calls Google, so it costs API requests, but every DB write becomes a `DRY RUN: would UPDATE ...` log line; `npm run enrich:dry-run -- --limit 5`). The local dev DB also has three unenriched places (Death & Co, Superiority Burger, Please Don't Tell) left `'pending'` on purpose for dry-run tests. Root `tsconfig.json` only includes `src/**`, so typecheck the script with `npx tsc --noEmit --strict --target es2022 --module nodenext --moduleResolution nodenext --skipLibCheck scripts/enrich-places.ts`. The local dev DB has three seeded East Village places (Veselka, McSorley's, Tompkins Square Bagels) that are already enriched.
- Google Places: the enrich script (`scripts/enrich-places.ts`) uses Places API (New) only, whose service is `places.googleapis.com`; `places-backend.googleapis.com` is the legacy Places API and does not serve `places:searchText`. Both are enabled on project `eve-enrich-2026` and the `eve-enrich` key (`projects/496847463127/locations/global/keys/31d70efe-22d4-4cba-b95f-b7fed756e72c`) is restricted to both. `gcloud services api-keys create` prints the `keyString` in its operation output even with `--format`; redirect everything to `/dev/null` and get the name from `api-keys list` (which omits the key string).
- `apps/mobile` is a root npm workspace (`workspaces: ["packages/*","apps/*"]`), so any `npm install` / `npx expo install` run inside it resolves against the ROOT `package-lock.json` (`cd apps/mobile && npm prefix` prints the repo root). `apps/mobile/package-lock.json` is still tracked and is a CI cache key, so after a mobile dependency change regenerate it in isolation: copy `package.json` + `package-lock.json` to an empty temp dir, run `npm install --package-lock-only --ignore-scripts` there, copy the lock back. Commit both lockfiles.
- iOS build numbering is local: `apps/mobile/eas.json` has `cli.appVersionSource: local`, so `expo.ios.buildNumber` in `apps/mobile/app.json` is the only source of truth (11 is the last used). Bump it by hand before a release build. `eas build:version:get` fails on purpose under local source. `eas build:configure` has no `--non-interactive` flag in eas-cli 18.10.0 or 25.3.0; run it with `</dev/null` instead.
- In prod, Caddy sends `/admin*` on the `.nyc` hosts to `eve-admin` (Next), so the Express EJS admin at `/admin` is only reachable by hitting `eve-app` directly. The EJS place form links to the Next admin via `NEXT_ADMIN_URL` (default `http://localhost:3001`; `deploy.yml` writes `https://eastvillageeverything.nyc/admin` into `/srv/eve/.env`). Photo uploads exist only in the Next admin since 1.7.
- Local dev stack: `docker compose up -d postgres redis` publishes Postgres on `127.0.0.1:5435` and Redis on `127.0.0.1:6381` (not 5432/6379). The host Node is v26, which breaks the `node-pg-migrate` CLI (yargs `require` in ESM scope); run migrations in a Node 20 container on the compose network: `docker run --rm -v "$PWD":/app -w /app --network eve_default -e DATABASE_URL=postgres://eve:eve_dev_password@postgres:5432/eve_development node:20-alpine node node_modules/node-pg-migrate/bin/node-pg-migrate up`. `PlaceModel`'s `validateUrl` only accepts absolute http(s) URLs, so the local admin needs `STORAGE_LOCAL_URL_PREFIX=http://localhost:3000/uploads` or saved photo URLs become null.
- S3 bucket `eastvillageeverything-uploads` (us-east-1) is versioned. The IAM user `eve-uploads` can only Put/Delete under `public/*` and cannot delete object versions; use root to purge. Its keys live in root `.env` as `STORAGE_AWS_ACCESS_KEY_ID` / `STORAGE_AWS_SECRET_ACCESS_KEY`.
- Local iOS builds need `SENTRY_AUTH_TOKEN` exported from root `.env` (`SENTRY_KEY`). EAS secrets are not delivered to local builds. See apps/mobile/README.md.
- Server typecheck needs the workspace packages built first: `npm run build:packages` then `npx tsc --noEmit`. See CLAUDE.md.
- The production site is `eastvillageeverything.nyc`. The `.com` domain is not ours.
- The deploy workflow rewrites `/srv/eve/.env` on every run. Anything that must persist on the host goes in a separate file.
- Since 1.3, `app` and `admin` in `deploy/docker-compose.prod.yml` both have `env_file: [.env, .env.storage]`. Anything the deploy workflow writes to `/srv/eve/.env` (such as `CORS_ORIGINS`) and anything in the host-only `/srv/eve/.env.storage` reaches both containers. `environment:` entries still win over `env_file` values.
